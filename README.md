## How deployment works

1. Push to `main` → the workflow logs in with **OIDC / federated credentials** (no stored secrets — only GUIDs in repo vars) and runs the auto-generated `azure-sentinel-deploy-*.ps1`.
2. The script recursively picks up **`*.json` and `*.bicep` files only** (excluding `*.parameters*.json`, `*.bicepparam`, `metadata.json`, `bicepconfig.json`).
3. Each file is validated with `Test-AzResourceGroupDeployment`, then deployed as a resource-group deployment. If the template declares a `workspace` string parameter, the script injects the target workspace name automatically — **declare that parameter in every template**.
4. Sentinel **metadata** records (linking each resource to this repo) are stamped for deployed content.
5. **Smart deployment:** file SHAs are tracked in `.sentinel/tracking_table_<id>.csv`, which lives on the `main-sentinel-deployment` orphan branch — only changed files re-deploy. Changing `sentinel-deployment.config` or setting `smartDeployment: false` forces a full re-deploy.

> ⚠️ **`.yaml` files are NOT deployed by this pipeline.** The two YAML files at the repo root (`RareOperations.yaml`, `TEST_RULE.yaml`) are portal exports and are currently inert — neither rule GUID exists in the workspace (confirmed against the 2026-10-04 export). `RareOperations` is deployed as ARM via [`analytics-rules/rare-subscription-level-operations.json`](analytics-rules/rare-subscription-level-operations.json); both YAMLs are safe to delete.

### Production rules (`analytics-rules/*.json`)

The 25 rules exported from `log-sentinel-cus` on 2026-10-04 (24 Scheduled + 1 NRT, all enabled) live here as one-file-per-rule ARM templates, named after the rule's display name. **Rule GUIDs are preserved from the workspace**, so deploying these files *adopts the existing rules in place* — no deletion or recreation needed, and incident linkage stays intact. 20 are linked to Microsoft gallery templates (`alertRuleTemplateName`); 4 are fully custom (Cowrie, 3× KeyVault HoneyToken).

> ⚠️ **The repo is the source of truth.** Portal-side edits to deployed content are overwritten on the next push. Keep changes here.

> ⚠️ **A push is a real deployment** to both workspaces. Review the diff accordingly.

## Per-type notes

- **Analytics rules** — resource name must be a **fixed GUID** (it's the rule ID; fixed = updates in place, `newGuid()` = duplicates every push). Durations are ISO 8601 (`PT1H`, `P14D`). `triggerOperator` uses ARM enum values (`GreaterThan`, not `gt`). Fast rules → `kind: "NearRealTime"` and drop `queryFrequency`/`triggerThreshold`.
- **Automation rules** — fixed GUID name, `order` sets execution precedence. `RunPlaybook` actions require the playbook to already exist and need the playbook's managed identity granted Sentinel Responder RBAC. Conditions: `conditionType: "Property"` with `propertyName`/`operator`/`propertyValues`; array conditions use `PropertyArray`.
- **Hunting queries vs parsers** — same resource type; the category string (`Hunting Queries`) is what the pipeline and the UI use to tell them apart. Parsers additionally set `functionAlias` (and optionally `functionParameters`).
- **Watchlists** — `itemsSearchKey` must be one of the item fields (it becomes `SearchKey` for joins). Treat the template as the source of truth: portal edits to items are re-asserted/overwritten on the next push. For big lists, deploy the shell via ARM and manage items via the Sentinel API.
- **Workbooks** — the workbook *instance* GUID is the resource name (fixed = idempotent). Get `serializedData` from the workbook's Advanced Editor (`</>` → ARM template tab). `sourceId` pointing at the workspace is what surfaces it in the Sentinel Workbooks gallery.
- **Playbooks** — ARM deploys the workflow, but the **Microsoft Sentinel API connection must be authorized once**: open the playbook in the Logic App designer, create/select the `azuresentinel` connection, save. Grant the playbook's managed identity Sentinel **Responder** (or Contributor for its own RG) RBAC. To attach a playbook to an analytics rule, add an `alertRules/actions` resource in the rule's template.

## Adding new content

1. Author the resource — easiest path: build it once in the portal, **export the ARM template**, and trim it to the single resource with `$schema`/`parameters` wrappers; or copy the closest sample here. Bicep works too (`.bicep` files are built by the pipeline).
2. Include a `workspace` string parameter and reference it in the resource name: `[concat(parameters('workspace'), '/Microsoft.SecurityInsights/<guid>')]`.
3. Use fixed GUIDs for Sentinel resource names; put the KQL/logic in `properties`.
4. PR → merge to `main` → the workflow deploys and stamps metadata. Deployment logs: GitHub Actions run for `Deploy Content to <workspace>`.

Optional `sentinel-deployment.config` (repo root; a change to it forces full re-deploy):

```json
{
  "parameterfilemappings": {
    "<workspaceId>": { "path/to/template.json": "path/to/params.json" }
  },
  "prioritizedcontentfiles": [ "path/to/playbook.json" ],
  "excludecontentfiles": [ "path/to/template.json" ]
}
```

Parameter file conventions: `template.parameters.json` (default) or `template.parameters-<workspaceId>.json` (workspace-specific).
